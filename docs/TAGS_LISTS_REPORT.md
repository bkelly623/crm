## Data model and unapplied SQL

Modified `prisma/schema.prisma` additively:

- `Tag`: bounded display name (60), globally unique normalized `nameKey`, creation timestamp.
- `LeadTag`: composite primary key `(leadId, tagId)`, timestamp and foreign keys to the existing master lead and tag.
- `LeadList`: name (80), owner Profile, unique `(ownerId, nameKey)`, creation timestamp.
- `LeadListMembership`: composite primary key `(leadId, listId)`, timestamp and foreign keys to the existing master lead and list.
- Added only virtual back-relations on existing `Profile` and `Lead`; **no existing scalar column/table changes**. No lead copying, embedded lead payloads, new lead creation, schema reset or alteration to Notes. Removing a membership removes a link, not a lead.
- Reverse tag/list indexes support membership lookup. Cascading foreign keys clean up links when a referenced record is removed, not the reverse.

**Review-only SQL:** `docs/schema-drafts/tags-lists.sql`. It is deliberately outside `prisma/migrations`, marked **DRAFT ONLY — NOT APPLIED**, and wrapped in a transaction. The DDL was generated by an offline diff between the original tracked schema and the new local schema. It creates four tables, four indexes and five foreign keys; no existing tables are altered. Added RLS enablement for all four new tables, with **no anon/authenticated policies**, to deny direct Supabase client access by default. Prisma's application authorization must still be enforced using an appropriately reviewed server database role. CUIDs are generated by Prisma, not SQL defaults.

Offline generation command (the baseline file was exported from `git show HEAD:prisma/schema.prisma` using file tools):


## API contract and authorization

| Endpoint | Contract |
| --- | --- |
| `GET /api/lead-organizers/{tags,lists}` | Catalog page: `{ items: [{ id, name, selected }], nextCursor }`. Optional `leadId` adds that accessible lead's membership flags; optional CUID `after` requests the next page. Without leadId, selected is false. |
| `POST /api/lead-organizers/{tags,lists}` | Strict `{ name }` payload; creates a tag or a self-owned list; 201 `{ item: { id, name } }`. Creating does **not** automatically add the current lead. |
| `PUT /api/leads/[id]/organizers/{tags,lists}` | Strict `{ organizerId }`; idempotently ensures the link; 200 `{ selected: true }`. |
| `DELETE /api/leads/[id]/organizers/{tags,lists}` | Same payload; idempotently removes the link; 200 `{ selected: false }`. |

Policy:

- Auth uses the existing verified Supabase user / persisted Profile helper, not client-supplied role or owner.
- `admin` / `sales_manager`: all leads and all lists.
- `sales_rep` / `closer` / `hybrid`: only leads assigned through setter **or** closer. Only their own lists are visible/manageable.
- `client`, `hiring_manager`, `project_manager`, unknown roles: denied even if assigned.
- Tags are a shared sales catalog; eligible sales staff can create them and change tags only on accessible leads. No tag rename/delete API.
- List ownership never grants access to an otherwise inaccessible lead. Catalogs expose no arbitrary lead IDs, member arrays or global membership counts. Membership queries repeat the lead scope in the relation predicate.
- Lead addition repeats assignment in the parent `Lead.update`. Nested upsert repeats list ownership in **both create and update connects**. The composite primary key prevents duplicate links; a unique-conflict race retries the same scoped operation once, never blindly reports success.
- Removal uses top-level link `deleteMany` with both lead scope and (for lists) owner/manager scope. Prisma nested `deleteMany` cannot express relation predicates. Zero deleted rows is idempotent after preliminary access checks. Concurrent loss of access cannot broaden the deletion; a zero-row result may also reflect a concurrent reassignment rather than an already-absent link.
- Adding via a parent lead update can advance its existing `updatedAt`; it never overwrites draft lead fields. Repeated requests guarantee membership state, not an immutable lead timestamp.

Validation and bounds:

- Exact kind enum; organizer IDs must be CUIDs (max 100), lead IDs nonempty/max 200 with surrounding whitespace rejected, not silently repaired.
- Names trim/collapse whitespace, reject control/format characters, enforce tag 60 / list 80 character bounds and a raw-input bound. Names retain display case; `nameKey` is lowercase. Duplicate names return 409, globally for tags and per owner for lists. This is not Unicode-confusable deduplication.
- Strict payload/query allowlists; malformed JSON and unknown fields rejected. Ownership cannot be injected.
- Catalog reads fetch at most 51 rows, return at most 50 with an exact next cursor. Membership operations affect one link; no bulk upload/change surface.
- Statuses: 401 anonymous; 403 denied role; 404 inaccessible/absent lead/list/tag or write-time missing record; 400 invalid input; 409 duplicate name; generic 500 for storage failures. Database details are not exposed.
- These are **organizational memberships**, not permission to call. Won/trashed/DNC leads are not silently interpreted as callable. No phone eligibility, consent, suppression, queue or dialer integration is claimed.

## Phone-friendly workspace

`LeadOrganizers` is mounted in the existing lead workspace, outside its lead edit form. The editor loads only after **Edit tags and lists** is pressed. Existing lead rendering/editing does not require the new tables, and missing-schema failures remain localized to the editor.

- Single-column phone / two-column wider editor, wrapping labels/actions, shrinkable containers, minimum 44px controls and 16px input text.
- Create a tag or self-owned list, then add/remove this lead using its entry button. Existing selected memberships show Remove actions.
- Independent tag/list loading, pending, validation, duplicate-name, network/storage error and success states; Reload and More controls. Pending controls are disabled and a synchronous in-flight guard prevents same-panel duplicate requests.
- Creation input and lead drafts survive errors. Membership state changes only after a successful matching server acknowledgement. Unknown outcomes advise retry/reload; retries target the same membership.
- No route refresh/navigation or lead-draft reinitialization during tag/list actions. Unsaved Notes/business edits remain in the original component state. Drafts still do not survive navigation/reload/tab loss, as in the existing workspace.
- Explicit text: **“Lists organize leads only; dialing is not connected.”** No fake calling/list-selection integration, no phone handoff, and no changes to the master lead list page or sequential dialer.
